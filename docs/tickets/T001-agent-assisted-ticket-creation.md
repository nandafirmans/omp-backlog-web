Add **Create with agent** to the new-ticket panel. User describes a feature, discusses it with an OMP agent, and receives an editable Markdown ticket. Prompt supports model selection, model-supported thinking levels, uploaded references, repository `@file` mentions and installed `/skill:NAME` mentions, reusing current editor behavior.

Research and proposed implementation: @docs/agent-ticket-drafting-research.md. This file is an importable implementation ticket, not a queued ticket; it deliberately lives outside `.omp-backlog/tickets`. When importing, choose an unused ticket ID.

Constraints:
- Reuse existing new-ticket Markdown/Preview editing, completion discovery, attachment rules, OMP RPC transport and validation. Keep manual creation/import available. No new AI SDK, scheduler or alternate ticket format.
- Drafting is separate from implementation execution. No ticket writes, approval, goal creation, scheduling, repository edits, shell commands or skill-script execution from the drafting agent. Do not change global model settings, project execution permission or scheduler pause state.
- Model and thinking selections apply to drafting only; enumerate installed OMP capabilities rather than hard-coding model names or efforts. Display effective selections and actionable discovery/provider errors. Reject unsupported selections; do not silently use another model. Refresh supported thinking efforts after a model change, accounting for provider-enforced/clamped thinking.
- Restrict drafting capabilities in the installed OMP version, including extension, plugin, custom-tool and configuration discovery. `--no-tools` alone is insufficient. Fail closed if executable discovery cannot be disabled. Use fresh private draft sessions, no implementation tools/host URI channels, and host-prepared selected context. This is not an OS sandbox.
- Context reads must independently enforce authentication, repository containment, regular-file/symlink checks, secret/private-path exclusions and byte/count limits. Completion results are not authorization. Resolve selected skill text without granting its instructions permission to execute tools or scripts.
- Treat prompts as conversation text, not arbitrary OMP RPC or executable slash commands. Do not expose shell, credential management or other privileged RPC commands through browser input.
- Preserve existing upload limits/types, descriptive references, staged-file retention, conflict handling and retry safety. Draft server uploads must remain private and outside watched tickets. Explain which documents/images were actually readable by the selected model; never claim an unread document was understood. Unsupported extraction/model input requires actionable disclosure, not fabricated content or silent omission.
- Bound turn/session resources, inbound RPC frame size and accumulated context. Cancel/timeout/provider failure must preserve user text, staged files and available partial output while settling/stopping only owned work. No automatic replay, budget increase or hidden provider calls before explicit drafting action. Concurrent drafting must not bypass global active-ticket ownership or interfere with an implementation run.
- **Use draft** transfers proposed Markdown into the existing editor only on user action. Protect unsaved human edits. Final creation remains explicit and validates ID collisions, frontmatter, dependencies, criteria and attachment references through current rules. No ID-allocation subsystem required.
- Preserve execution policy: Automatic may execute a valid created ticket under standing permission; explicitly warn before creation. Cancel must not persist a ticket. Approved-only still needs exact-revision approval; Paused still prevents starts. Drafting itself must never create a scheduler-visible ticket in any mode.
- Tab-local conversation/draft persistence is sufficient if disclosed; durable chat history and reload recovery are not required. Never expose credentials, session files, private configuration or uploaded context to unauthenticated requests or logs.
- Before the first provider turn, enforce a fixed drafting launch profile with executable discovery disabled before module loading, not merely hidden after startup. Do not launch from the selected repository if that permits project-code discovery. Disable goal continuation, automatic retry and cache warming for this session. Reject unexpected tool/host-URI/UI requests, stop the owned child, and preserve the conversation. Pass user content inside a host-owned drafting envelope so leading slash commands cannot dispatch OMP local commands. Never accept executable paths, launch arguments, RPC command names or session paths from browser input.
- Each selected reference must show a host-recorded preparation state: pending, ready, unsupported or failed, including whether extraction was partial. These states describe prepared/transmitted bytes, not proof of model understanding. Block Send while selected required context is pending, failed, unsupported or silently truncated; user can replace it or explicitly exclude it from model context while retaining a visible reference-only attachment. Model changes must revalidate included image/context support.
- Drafting and draft-upload routes must not call ticket writes, approvals or scheduler mutation functions. Final assisted creation must revalidate the reviewed Markdown, attachment set and current project mode server-side. Bind Automatic-mode confirmation to that reviewed payload and mode; reject stale confirmation and require review again if either changed. Do not silently switch project mode or invent a Draft-status exemption.
- Publish assisted-created tickets only after the complete reviewed Markdown and selected attachment bytes are validated and staged outside watched storage. Prevent scheduler admission of intermediate/partial creation state, including a no-attachment ticket becoming eligible before selected uploads finish. Failed publication must preserve draft recovery without duplicate tickets; use the repository's existing serialization/conflict conventions. Keep existing manual creation available and do not relax its gates.

Done when:
- From New ticket, user can choose agent-assisted creation or continue manual Markdown/import without regression. Agent composer supports keyboard-accessible model/thinking selectors, prompt entry, Send and Cancel on desktop/mobile layouts.
- A user can describe a feature, receive clarification, answer it, refine the proposal in follow-up turns and explicitly transfer a complete editable ticket containing title, dependencies, request and observable `Done when:` criteria into Markdown/Preview. No silent overwrite of human edits occurs.
- Model discovery and selection use installed OMP RPC; thinking choices refresh for the selected model. Visible effective selections govern subsequent turns, unsupported choices fail clearly, and controls cannot race an active turn. Drafting never mutates execution settings.
- `@` and `/skill:` completion retain current loading/no-match/error, keyboard selection and quoted-space-path behavior. Selected repository/skill context reaches the agent through safe bounded resolution. Direct requests for excluded paths, traversal, symlinks or credentials are rejected even if completion is bypassed.
- User can upload/paste supported references, see included context, use supported images/readable documents during drafting and retain purpose-labeled attachments in the final ticket. Unsupported document extraction or model input is explained before sending that context; oversized frames/files are rejected without losing draft or attachments.
- Send starts only an explicitly authorized drafting turn. Empty/discovery/provider errors, cancellation and timeout do not create tickets or approvals, replay work, alter modes or lose existing user input. Available partial agent output remains inspectable and owned processes/temp uploads are safely bounded and cleaned up.
- Capability checks demonstrate that drafting cannot invoke built-in writes/shell tools, custom/plugin/extension execution, host URI access, privileged RPC or implementation result/goal tools. Referenced skill/upload instructions cannot grant these capabilities. Missing enforceable restriction prevents drafting launch rather than falling back to an unrestricted agent.
- In a disposable Automatic project, a complete generated ticket remains absent from ticket storage/state and no implementation run starts before explicit Create ticket. Automatic-mode creation warns about possible execution; cancel preserves drafts. Independently verify Paused creation prevents starts and Approved-only creation requires exact-revision approval. Existing dependency, handoff and global ownership gates remain effective.
- Explicit creation persists the reviewed Markdown and attachment bytes exactly once through existing write/upload paths. Exercise duplicate-ID conflict, interrupted upload/retry and external revision conflict without duplicate tickets, lost edits or mismatched attachment references.
- In disposable capability fixtures, configure synthetic project/global extension and custom-tool discovery entries that would write a sentinel if loaded; drafting must not load them or create that sentinel. Exercise forged browser RPC/launch parameters, a leading executable slash command and unexpected tool/URI requests; reject them without repository changes. This fixture does not establish OS sandboxing or live-provider availability.
- Exercise image-capable to text-only model switching, unsupported PDF/Office extraction, extraction failure, partial extraction and oversize context. UI must identify exactly what will be sent, block unresolved selected context and require explicit exclusion/replacement; reference-only attachments remain available for final ticket review.
- In Automatic mode, exercise creation while an upload is still staged or failing, and change project mode or reviewed content after confirmation. No partially published ticket is admitted; stale confirmation fails before publication. A successful retry creates one complete ticket with the reviewed bytes. Drafting endpoints cannot create/approve tickets even when called directly rather than through the UI.
- Before claiming the feature complete, record an explicitly authorized live OMP/provider browser journey covering selected model/thinking, one follow-up, safe file/skill context and supported upload input through final editable handoff. Separately record host capability fixtures and mode/publication checks; if provider access or enforceable tool isolation is unavailable, preserve partial evidence and report the feature blocked rather than complete.
- Verify changed journeys in a real browser using disposable projects/private data and applicable `/skill:verify-backlog` guidance. Add/update behavior tests following repository conventions and lint changed code; no production build solely for verification. Keep protocol-fixture and live-provider evidence distinct, and never present unperformed checks as passing. Update README/current workflow and affected verification-map entries with implemented behavior and limitations.

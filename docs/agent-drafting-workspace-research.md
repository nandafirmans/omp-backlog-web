# Agent drafting workspace: drawer or page?

Research date: 2026-10-24. Research only; no product changes or usability testing. External searches used generic product/design questions, not project content.

## Recommendation — synthesis, not a source mandate

**Keep direct manual creation in its existing drawer; give optional “Create with agent” a dedicated full-page workspace.** Use two explicit views, **Discuss** and **Review ticket**, rather than stacking conversation, context controls and the complete manual editor in one scrolling drawer. Preserve the same draft/session across view changes. A full page does not require a multi-column “AI cockpit.”

The reported 800px drawer contains two substantial activities: developing the request through conversation and reviewing/editing the publishable ticket. Separating the agent into another drawer removes the manual form from its immediate viewport, but does not by itself resolve extended conversation, context inspection and review navigation. A page is the stronger fit for this scope under Fluent's prolonged-task guidance and Carbon's complex-flow guidance. This is a design inference, not evidence that a drawer cannot work. [1–2]

## What the primary sources actually say

| Source | Source guidance or documented behavior | Implication for this decision — our interpretation |
| --- | --- | --- |
| **Microsoft Fluent 2: Drawer** [1] | Drawers are secondary surfaces for supplemental information/simple actions. Inline drawers support simultaneous interaction with parent content; overlay drawers are modal by default. Keep multistep drawers to two–three steps; consider a more focused surface for longer/complex work. Do not invoke multiple overlay drawers at once. Warn about progress loss on dismissal. | An independent agent drawer is defensible for a short contextual subtask, especially when the board must remain interactive. It is less compelling for an open-ended drafting session. If chosen, replace the manual drawer rather than layering another over it. |
| **IBM Carbon: Modal** [2] | Modals interrupt work for short, non-frequent tasks. Repeated tasks may belong on the main page. If the largest modal still requires excessive scrolling, consider a page. Complex flows with complex choices may need a full page; a progress modal is not a cure for excess content. | Widening a drawer or putting the same stack behind wizard steps is not automatically a simplification. Prefer a focused workspace when the conversation, context and final editor all require substantial attention. This modal guidance applies specifically when the drawer behaves modally. |
| **Linear: Issues** [3] | Standard creation opens a modal. Linear also documents URL-based creation entry points. Navigating away hides the modal and retains a client-local temporary draft; closing with Escape or the close button offers saving a persistent draft. | Preserve the fast manual path. Leaving, hiding and discarding a draft are different actions and should have explicit semantics. This source does **not** establish that Linear's URL entry points render a full-page editor. |
| **GitHub: Copilot issue creation** [4] | The documented flow starts in Copilot, accepts prompts/images, drafts structured issue fields, allows direct edits or follow-up prompts, and requires an explicit **Create** action. Existing issue updates are reviewed in a workbench. | Conversation and the resulting ticket are distinct representations of the same task. Provide a visible review/edit handoff and keep publication separate from sending a prompt or accepting generated text. This supports interaction structure, not a mandatory two-column layout. |
| **W3C WAI-ARIA APG: Modal dialog** [5] | Modal backgrounds are inert. Focus enters the dialog, Tab/Shift+Tab stay inside, Escape closes it, and focus normally returns to its invoker. Include a visible close control. For long/structured content, initially focusing a static heading may be preferable; avoid treating the entire structure as one `aria-describedby` string. Only mark truly modal behavior `aria-modal="true"`. | A modal drawer does not actually preserve access to the board, even when the board remains visible. A real page avoids maintaining a long-lived focus trap; it still needs deliberate heading/focus management. Do not mark an interactive side-by-side workspace modal. |

## Concrete interaction proposal

These are recommendations for a later implementation, not claims about current behavior or additional approved scope.

1. **Entry:** retain **New ticket** as the immediate manual route. Offer **Create with agent** as an optional sibling action, not a mandatory first step. The agent page identifies the project and provides a clear return to the board. A route such as `/projects/:repoId/tickets/new/agent` is a proposal only, not a claim about current routing.
2. **Discuss:** make conversation the primary content with the composer directly reachable. Keep explicit connect/disconnect and session status visible. Group model/thinking controls near the composer; show selected context as a compact summary with an expandable inspection area. Keep unresolved context, validation and exclusions visible beside their affected items rather than hiding them in transcript prose. Retain paste and `@file`/`/skill` completion. Preserve the current capability-restricted drafting boundary: selected context informs drafting, not permission to write files, run commands or implement. Fluent explicitly recommends placing status feedback near the affected content. [1]
3. **Review ticket:** **Review proposal** opens the editable ticket as the primary surface. **Back to discussion** retains both conversation and human edits. Do not automatically replace edited Markdown when another proposal arrives. Avoid showing the complete chat and editor simultaneously by default; a compact proposal indicator is enough to bridge the views. This follows GitHub's draft–review–create distinction without copying an unverified layout. [4]
4. **Publication:** only **Create ticket** publishes. Preserve the existing confirmation bound to the reviewed payload and current project mode; keep the Automatic-mode execution warning always visible in the final Review view, not only in chat or a later confirmation. Moving the UI must not weaken this contract. See the existing [agent-assisted creation contract](current-agent-workflow.md#agent-assisted-creation).
5. **Leaving:** distinguish returning to the board, disconnecting the owned OMP child and discarding the draft. Do not silently equate these actions. Preserve explicit **Disconnect** stopping the owned child. Disclose tab-local limits honestly: reload loses conversation/files; a dedicated URL alone does not create resumability. Linear's stronger persistent-draft behavior is a reference pattern, not an existing OMP capability. [3]
6. **Small screens and zoom:** show Discuss or Review as one primary surface, not two narrow columns. Keep essential actions reachable without allowing fixed controls to consume most of the viewport; Fluent specifically relaxes sticky drawer headers/footers at 400% zoom and small viewports. [1]

## When a separate drawer would be the better choice

Choose it if the intended experience is deliberately brief and users need to keep consulting/interacting with the board. Use one agent surface, an explicit handoff to the manual editor, and no simultaneously stacked overlay drawers. An inline/non-modal panel preserves actual board access; an overlay/modal panel preserves only visual context. If the panel needs its own extended discussion, context inspector and full editor, it has become the workspace the page proposal is meant to accommodate. [1, 5]

## Limits of the evidence

- These are official guidance and documented product patterns, not comparative usability results. No user sessions, prototype evaluations, accessibility audits or browser checks were performed for this note.
- Fluent's drawer page is labeled **Preview**. Its two–three-step guidance is a design heuristic, not a universal maximum or accessibility requirement. Carbon's modal rules should not be applied indiscriminately to inline drawers.
- Linear and GitHub document what their products do, not why it is optimal for this app. GitHub labels this issue-creation feature **public preview**. Neither source proves that a dedicated page will outperform a well-designed drawer here.
- WAI-ARIA APG is implementation guidance, not itself the normative WCAG specification or a certification of either design. A page is not inherently accessible; modal correctness alone does not establish usability.
- Draft preservation, deep-linking and persistence are separate engineering decisions. This recommendation does not claim that any are already implemented beyond the current documented contract, or authorize building them.
